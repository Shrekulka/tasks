# Бот «Лісові поради»

Telegram-бот: звірі ставлять запитання, а бот відповідає на основі спільної бази документів і вказує джерело.
Звірі можуть самостійно поповнювати базу, надсилаючи документи у форматах PDF, Word і TXT.

## Можливості бота

- Відповідає на запитання **лише за документами з бази**, українською мовою та вказує джерело під кожною відповіддю. Для документа з архіву джерело — «Лісовий архів». Для документа, доданого користувачем, указуються назва документа, сторінка, ім’я автора, `@username` і час завантаження за київським часом.
- Якщо відповідного фрагмента немає, чесно повідомляє про це й нічого не вигадує.
- Приймає документи PDF, DOCX і TXT розміром до `MAX_FILE_MB` МБ. Дублікати за SHA-256 не індексуються; бот повідомляє, хто і коли вже додав документ. Скановані PDF без текстового шару відхиляються.
- Команда `/mydocs` показує список власних документів із розбиттям на сторінки та дає змогу видалити документ після підтвердження. Видаляти чужі документи й документи архіву не можна.
- Під час кожного запуску перевіряє стандартні документи в каталозі архіву (`ARCHIVE_HOST_DIR`): додає нові файли, повторно індексує змінені й вилучає видалені.
- Працює лише в особистих повідомленнях. У групах у відповідь на команди надсилає підказку.

## Керування власними документами: `/mydocs`

Команда `/mydocs` показує документи, додані поточним користувачем.

### Наскрізна перевірка завантаження TXT, пошуку та відповіді

![Завантаження тестового TXT і три відповіді на запитання за його вмістом із зазначенням джерела](docs/screenshots/02-rag-e2e-three-answers.png)

На знімку показано ручний E2E-сценарій: від завантаження `rag_e2e_test_winter_animals.txt` до відповідей на три запитання. Це не сценарій із mock-об’єктами: запитання ставилися через Telegram запущеному боту з підключеним LLM-провайдером.

**Результат ручної перевірки 23.10.2026:** документ `rag_e2e_test_winter_animals.txt` записано до PostgreSQL зі статусом `ready`; `chunk_count = 2`, у таблиці `chunks` фактично знайдено два рядки. На три контрольні запитання отримано очікувані факти з джерела `rag_e2e_test_winter_animals`:

1. Контейнер і місце: синя металева коробка під третім пласким каменем біля старого дуба на західному краю галявини.
2. Маркування та періодичність перевірки: помаранчева мотузка з двома вузлами; перевірка кожні чотири дні.
3. Контрольний факт: точний код `ДУБ-731-КВАДРО`.

Це підтверджує роботу одного наскрізного сценарію, але саме по собі не є статистичною оцінкою якості RAG для довільних запитань.

#### Як повторити E2E-перевірку

1. Запустіть сервіси командою `docker compose up -d` і дочекайтеся повідомлення `Start polling` у журналі бота.
2. Надішліть боту в Telegram файл [`docs/examples/rag_e2e_test_winter_animals.txt`](docs/examples/rag_e2e_test_winter_animals.txt) як документ.
3. Поставте запитання:
   - «У чому борсук Данило зберігає жолуді та де саме він сховав коробку?»
   - «Як позначено коробку і як часто Данило перевіряє запас?»
   - «Який вигаданий код записано в записнику Данила?»

##### Запитання, відповіді на яке немає в документах (T4)

Додатково запитайте бота: «Який номер паспорта має борсук Данило?».

Очікуваний результат: бот чесно повідомляє, що не знайшов відповіді в документах, нічого не вигадує та не додає блок «Джерела».

![Бот повідомляє, що відповіді в документах немає, без блоку джерел](docs/screenshots/06-no-answer-response.png)

*Ручна перевірка T4: тестовий документ не містить відповіді на запитання, тому бот повертає заздалегідь визначене повідомлення про відсутність відповіді без джерел.*

4. Перевірте запис і фрагменти в PostgreSQL. Ідентифікатор документа може відрізнятися від `10` залежно від стану бази даних.

Перевірка реєстру документів і кількості фрагментів:

```bash
docker compose exec -T db sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT
    d.id,
    d.filename,
    d.status,
    d.chunk_count,
    COUNT(c.id) AS actual_chunks
FROM documents AS d
LEFT JOIN chunks AS c ON c.document_id = d.id
WHERE d.filename = 'rag_e2e_test_winter_animals.txt'
GROUP BY d.id, d.filename, d.status, d.chunk_count;
SQL
```

Очікуваний результат: `status = ready`, а `chunk_count` дорівнює `actual_chunks` (у перевіреному запуску — `2 = 2`).

![Тестовий документ у PostgreSQL: статус ready, два фрагменти й два фактичні записи](docs/screenshots/04-database-ready-counts.png)

*Тестовий документ `rag_e2e_test_winter_animals.txt` успішно проіндексовано: значення `chunk_count` збігається з кількістю записів у таблиці `chunks`.*

Перегляд проіндексованого вмісту:

```bash
docker compose exec -T db sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT d.id, d.title, c.chunk_index, c.content
FROM documents AS d
JOIN chunks AS c ON c.document_id = d.id
WHERE d.filename = 'rag_e2e_test_winter_animals.txt'
ORDER BY c.chunk_index;
SQL
```

![Два проіндексовані фрагменти тестового TXT-документа в PostgreSQL](docs/screenshots/05-indexed-chunk-content.png)

*У таблиці `chunks` збережено вміст вихідного файла, доступний для семантичного пошуку.*

На скриншотах Telegram видно відображуване ім’я та `@username`. Перед публікацією перевірте, чи можна розкривати ці дані, або підготуйте копії з належним маскуванням.

## Оцінювання якості пошуку та поріг релевантності

`RELEVANCE_THRESHOLD` — це максимальна косинусна відстань, за якої фрагмент вважається релевантним. Значення залежить від моделі ембедингів, тому поріг потрібно підбирати на даних, а не навмання. Набір контрольних запитань розташовано в `tests/eval/questions.json`: там є запитання з відповідями, запитання російською мовою, два суперечливі документи й запитання, відповіді на які в документах немає.

```bash
python -m scripts.eval_retrieval                # для samples/archive
python -m scripts.eval_retrieval --archive ./archive --questions свої_питання.json
```

Скрипт індексує каталог у пам’яті за допомогою реальної моделі з `.env`, перебирає пороги та формує звіт у Markdown із рекомендацією `RELEVANCE_THRESHOLD=…`. База даних і LLM не потрібні, тому денна квота OpenRouter не витрачається. Після оцінювання встановіть рекомендоване значення `RELEVANCE_THRESHOLD` у локальному `.env`; якщо значення підходить як типовий параметр для інших запусків, оновіть також `.env.example`. Збережіть звіт оцінювання разом із документацією проєкту.

**Принцип налаштування — спочатку повнота.** Абсолютні відстані в моделей e5 мають стислий діапазон: релевантні й нерелевантні фрагменти часто розташовані близько один до одного, тому ідеального порога зазвичай немає. Відхилити запитання, на яке в документах є відповідь, гірше, ніж зайвий раз звернутися до LLM: вона може повернути `found=false` і спрацює як другий рівень захисту. Тому скрипт шукає пороги, які не втрачають запитань із відповідями (`--min-recall`, типове значення — 100%). Серед них він обирає поріг, що відхиляє найбільше зайвих запитань, і рекомендує середину відповідного діапазону: вона стабільніша за граничний максимум. Параметр `--margin 0.05` додатково відсіює «хвіст» слабко пов’язаних документів після найкращого збігу; у `.env` йому відповідає `RELEVANCE_MARGIN`.

Під час локального запуску (поза Docker) після першого завантаження моделі задайте в оточенні `HF_HUB_OFFLINE=1`, щоб `sentence-transformers` не звертався до Hugging Face під час кожного запуску. У Docker цю змінну вже ввімкнено.

Дублікати в архіві: основним документом вважається файл, назва якого перша за лексикографічним порядком (наприклад, `a.txt` перед `a_copy.txt`); решта дублікатів пропускається, про це з’являється попередження в журналі.

## Архітектура

`handlers/` (тонкі обробники) → `services/` (приймання документів, пошук і формування відповідей) → `models/` (PostgreSQL + pgvector) та `external_services/llm/` (безкоштовні моделі OpenRouter: динамічний список, перебір моделей, карантин і облік денної квоти). Докладніші вимоги й архітектурні рішення описано в `docs/requirements.md`.

> **LLM-провайдер.** Замість Groq, зазначеного в завданні, використовуються безкоштовні моделі OpenRouter: доступ до Groq для облікового запису автора обмежений. Провайдер підключається через адаптер (`external_services/llm/registry.py`), тому код бота від нього не залежить. Ліміти безкоштовних моделей OpenRouter спільні для всього облікового запису, тому додано кешування відповідей та облік квоти.

> **Приватність.** Документи й ім’я автора видимі всім звірам. Бот попереджає про це під час завантаження та в команді `/help`.

## Запуск у Docker (основний спосіб)

Потрібен Docker Desktop або Docker Engine із плагіном Compose.

1. Створіть бота в Telegram: напишіть `@BotFather`, виконайте команду `/newbot` і скопіюйте токен.
2. Підготуйте налаштування:

   ```bash
   cp .env.example .env
   ```

   Заповніть у `.env` два значення: `TELEGRAM_BOT_TOKEN` (токен від `@BotFather`) і `LLM_API_KEYS` (ключ OpenRouter із розділу Keys на openrouter.ai). Без справжнього ключа LLM бот не запуститься. Не додавайте файл `.env` до репозиторію.

3. Запустіть застосунок:

   ```bash
   docker compose up --build
   ```

4. Напишіть своєму боту команду `/start`.

![Стан Docker-контейнерів, ініціалізація PostgreSQL і запуск Telegram polling](docs/screenshots/03-docker-startup-and-health.png)

*PostgreSQL готова до роботи, pgvector і таблиці ініціалізовано, модель ембедингів завантажено, Telegram polling запущено.*

Корисні команди:

```bash
docker compose logs -f bot     # журнали бота
docker compose down            # зупинити сервіси (дані бази збережуться)
docker compose down -v         # зупинити сервіси й ВИДАЛИТИ дані бази
```

## Інша мова відповіді

Мову відповідей задають конфігураційні дані, а не код:

1. `data/languages/<код>.json` за зразком `uk.json`: поле `answer_phrase` і параметри перевірки мови.
2. `data/prompts/<код>/system.txt` (за потреби також `strict_reminder.txt`): власний текст промпта. Якщо його немає, використовується загальний `data/prompts/system.txt`, у якому мову відповіді підставлено як `$answer_phrase`.
3. `ANSWER_LANGUAGE=<код>` у `.env`.

Версія промпта в ключі кешу визначається за кінцевим текстом, тому відповіді різними мовами не змішуються.

**Що залишається українською.** Тексти інтерфейсу бота (привітання, повідомлення «не знайшов», підписи джерел і повідомлення про помилки) містяться в `lexicon/lexicon_uk.py`: відповідно до вимог інтерфейс має бути одномовним (D20). Зміна `ANSWER_LANGUAGE` змінює мову відповіді моделі, але не мову цих текстів. Для повної локалізації знадобиться окремий файл `lexicon_<код>.py` і вибір модуля відповідно до налаштування.

## Обмеження та відомі недоліки

- **Безкоштовні моделі OpenRouter.** Станом на перевірку 23.10.2026 офіційна сторінка вказує 20 запитів на хвилину та 50 на день для моделей `:free`. Збільшений денний ліміт пов’язаний із придбанням кредитів, яке в проєкті не використовується. Перевіряйте актуальні умови на сторінці [OpenRouter Pricing](https://openrouter.ai/pricing) і в [документації щодо лімітів API](https://openrouter.ai/docs/api-reference/limits).
- Бот чесно повідомляє про вичерпання квоти; відповіді кешуються, а запитання без відповідних фрагментів і привітання не надсилаються до LLM.
- **Локальний лічильник квоти** є приблизним: джерелом істини залишається провайдер, а залишок повторно читається з `GET /key`.
- **Перевірка мови відповіді евристична** (`data/languages/`). На корпусі `tests/eval/language_cases.json` вона не відхиляє коректну українську, але може пропускати деякі короткі російські фрази без характерних слів. Метрики перевіряються тестом `tests/unit/test_language_corpus.py`.
- **Поріг релевантності** залежить від моделі ембедингів, префіксів і розбиття на фрагменти. Після будь-якої зміни цих параметрів запустіть `python -m scripts.eval_retrieval` і перегляньте `RELEVANCE_THRESHOLD`.
- **OCR не реалізовано:** PDF без текстового шару відхиляються з поясненням.
- Запитання незалежні одне від одного; бот не зберігає історію діалогу.

## Остання підтверджена перевірка

У локальному середовищі 23.10.2026 зі змінною `TEST_DATABASE_URL`, що вказувала на PostgreSQL із pgvector, повний набір тестів завершився результатом **515 passed in 12.12s**. Також пройшли `ruff check .` і `ruff format --check .`. Docker-образ бота зібрано; у Docker Compose PostgreSQL перейшла в стан `healthy`, модель ембедингів завантажилася, а в журналі з’явилося повідомлення `Start polling`.

Після надсилання тестового TXT через Telegram PostgreSQL показала статус `ready` і відповідність `chunk_count=2` двом фактичним фрагментам. На три контрольні запитання отримано очікувані відповіді із зазначенням джерела. Ці результати стосуються перевірки від 23.10.2026 і не гарантують такої самої якості для всіх документів.

## Розробка

Потрібен Python 3.12.

```bash
python3.12 -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
cp .env.example .env                 # потім заповніть значення
```

Запускайте перевірки після кожної зміни:

```bash
ruff check .
ruff format --check .
pytest
```

Тести з міткою `integration` потребують справжнього PostgreSQL із pgvector і за замовчуванням пропускаються. Щоб їх запустити, підніміть базу (`docker compose up -d db`) і задайте адресу підключення:

```bash
TEST_DATABASE_URL=postgresql+asyncpg://USER:PASSWORD@127.0.0.1:5432/DB pytest
```

Порт бази даних у головному compose-файлі не публікується назовні. Для тестів використовуйте додатковий compose-файл:

```bash
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d db
```
