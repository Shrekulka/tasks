# Teremok Parser

Парсер оголошень з [teremok.org.ua](https://teremok.org.ua/) — тестове завдання: 200 найновіших оголошень, ≥5 категорій, всі публічні поля, дедублікація, позначення відсутніх даних, експорт у CSV / JSON / Excel.

```
python -m teremok_parser --mode quota_coverage
```

---

## 1. Результат одним поглядом

| Вимога ТЗ | Реалізовано |
|---|---|
| 200 найновіших оголошень | ✅ 200 записів, відсортовані за `published_at` (спадання) |
| ≥5 категорій | ✅ 5 категорій: транспорт, дитячий одяг, телефони, нерухомість, меблі |
| Усі публічні поля | ✅ title, description, price(+currency), category, city, published_at, seller, views, images[], characteristics{}, url |
| Видалення дублікатів | ✅ 2 рівні: точні (hash) + близькі (той самий продавець + схожа назва) |
| Позначення відсутніх полів | ✅ єдиний маркер `"немає даних"` + звіт про повноту по кожному полю |
| Формати виводу | ✅ `.csv`, `.json`, `.xlsx` — усі з одного запуску |

Кожен запуск генерує **звіт про якість даних** (`teremok_report.json`) — скільки зібрано, скільки видалено дублів, розподіл по категоріях, повнота полів. Це не рекламний текст, а перевірювані цифри з реального прогону.

## 2. Архітектура

Головний принцип — **Separation of Concerns**: кожен шар відповідає рівно за одну річ і нічого не знає про сусідні. HTTP-клієнт не знає, як парсити оголошення; парсер не знає, куди експортувати Excel; селектор не знає деталей HTTP і т.д. Це навмисне рішення заради довгострокової підтримки: якщо на сайті зміниться верстка картки оголошення — правиться лише `parser/listing.py`, решта пайплайну не торкається. Якщо знадобиться нова стратегія відбору — новий модуль у `selection/`, і так далі.

```
┌──────────────────────────────────────────────────────────────────────┐
│                         CLI & ENTRY POINT                            │
│           teremok_parser/main.py  ◄───►  teremok_parser/cli.py       │
└────────────────────────────────┬─────────────────────────────────────┘
                                  ▼
┌──────────────────────────────────────────────────────────────────────┐
│                      PIPELINE ORCHESTRATOR                           │
│                 teremok_parser/pipeline/scraper.py                   │
└──────┬─────────────────┬──────────────────┬──────────────────┬───────┘
       ▼                 ▼                  ▼                  ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  TRANSPORT   │  │   PARSING    │  │  SELECTION   │  │ DEDUPLICATOR │
│ HTTP/robots  │  │BeautifulSoup │  │ newest/quota │  │ exact / near │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       ▼                 ▼                 ▼                 ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ RAW STORAGE  │  │ DOMAIN MODEL │  │  VALIDATION  │  │  EXPORTERS   │
│ лише --debug │  │ Pydantic v2  │  │Hard Gate +   │  │Excel/CSV/    │
│              │  │   Listing    │  │телеметрія    │  │JSON/Report   │
└──────────────┘  └──────────────┘  └──────────────┘  └──────────────┘
```

Дані на виході кожного запуску складаються в окрему теку за `run_id` (розділ 4) — прогони не перезаписують один одного, історію можна порівнювати.

**Стек:** `requests` + `BeautifulSoup4/lxml` (парсинг), `Pydantic v2` (валідація моделі оголошення), `pandas` + `openpyxl` (експорт), `pytest` (тести). Без екзотичних залежностей — усе, що потрібно підтримувати команді в довгостроковій перспективі.

## 3. Особливості та нюанси, які варто знати

### 🎯 Два режими відбору оголошень

ТЗ містить приховане протиріччя: "200 найновіших" і "≥5 категорій" одночасно тягнуть у різні боки — якщо просто взяти 200 найсвіжіших по всьому сайту, велика категорія (транспорт) витіснить дрібні. Тому є два режими:

- **`quota_coverage`** (за замовчуванням) — гарантує мінімум N оголошень на категорію, залишок добирає найсвіжішими. Використано для фінального датасету.
- **`strict_newest`** — бере строго 200 найновіших без квот; категорій може вийти менше або нерівномірно.

> ⚠️ **Важливий нюанс для замовчика**: обидва режими сканують лише 5 наперед заданих категорій (не весь сайт). Тобто "200 найновіших" — це найновіші **в межах цих 5 категорій**, а не глобально по ресурсу. Якщо потрібен саме глобальний зріз — це змінюється додаванням автовиявлення категорій (пункт 6).

### 🧹 Дедуплікація у два кроки

1. **Точні дублі** — hash по нормалізованому title+description+price. Ловить копії, розміщені двічі.
2. **Близькі дублі** — той самий продавець + схожа назва (нормалізація регістру/пробілів). Ловить типові "той самий товар, трохи інший опис".

### 🚫 Позначення відсутніх даних

Усі поля, яких немає в оголошенні (не вдалося витягти або продавець не заповнив), явно позначаються `"немає даних"` — жодних порожніх рядків чи `null`, що можна сплутати з помилкою парсингу. У звіті окремо рахується % заповненості кожного поля — видно, які дані на сайті взагалі рідко заповнюють.

### 🔒 Hard Gate — захист від "тихого" браку

Перед експортом датасет проходить перевірку інваріантів (немає дублів по URL/id, ціни невід'ємні, дати не з майбутнього і т.д.). Якщо перевірка не пройдена — **файл не експортується**, пайплайн падає з чіткою помилкою. Це навмисно: краще зупинити прогін, ніж віддати замовнику биті дані.

### 💰 Ціни та дати без втрати точності

- Ціни парсяться в `Decimal` (не `float`) — не накопичується похибка округлення.
- Дати конвертуються з `Europe/Kyiv` у `UTC` явно, з окремим полем `published_at_raw` (як було на сайті) — для аудиту, якщо парсинг дати колись піде не так.

### 📊 Концентрація продавців (бонус, не було в ТЗ)

Звіт додатково показує, чи не розміщує один продавець аномально багато оголошень — корисний сигнал для модерації/антиспаму на дошці оголошень, актуальний саме для цього типу проєкту.

### 🌐 robots.txt та поведінка мережі

Парсер читає `robots.txt` і **не сканує заборонене** — у разі мережевої помилки під час його завантаження обирає безпечний варіант (fail-closed, тобто не сканує, а не навпаки). Запити йдуть із затримкою, ретраями та jitter — щоб не створювати навантаження на сайт і не потрапити під блокування.

## 5. Запуск і режими — детально

### 5.1. `--mode` — як саме відбираються 200 оголошень

Це головний параметр, і від нього залежить, **який саме** датасет ви отримаєте на виході. Механіка обох режимів:

1. Усі зібрані оголошення групуються по категоріях і сортуються всередині кожної — від найновішого до найстарішого.
2. Далі — розбіжність:

```bash
python -m teremok_parser --mode quota_coverage
```
**Крок 1 — "бронювання" місць по категоріях.** З кожної категорії береться мінімум `min_per_category = 10` найновіших оголошень (навіть якщо в іншій категорії є свіжіші — вони почекають).
**Крок 2 — добір решти.** Місця, що залишились до 200, заповнюються найновішими оголошеннями з усього пулу, незалежно від категорії.

Результат — реальний розподіл з нашого прогону:

| Категорія | Кількість | Звідки взялись |
|---|---|---|
| Продаж транспорту | 105 | 10 гарантованих квотою + 95 добрані як найновіші (категорія дуже активна) |
| Дитячий одяг | 45 | аналогічно — активна категорія |
| Мобільні телефони | 26 | — |
| Квартири, кімнати | 14 | — |
| Меблі для кухні | 10 | тільки гарантована квота — нових оголошень мало, і без квоти категорія взагалі могла зникнути з вибірки |

```bash
python -m teremok_parser --mode strict_newest
```
Кроку 1 немає. Просто беруться 200 найновіших оголошень з усього пулу без жодних гарантій по категоріях. Якщо, наприклад, за останню добу 190 з 200 нових оголошень — це вживані авто, а меблі оновлюються рідко, то в підсумковому датасеті меблів може взагалі не бути.

**Коли який використовувати:**

| Ситуація | Режим | Чому |
|---|---|---|
| Потрібен зріз "що зараз найактуальніше" (моніторинг, аналітика попиту) | `strict_newest` | Чесно показує реальну активність по сайту — де більше нових оголошень, там і буде більше в вибірці |
| Потрібен збалансований датасет для імпорту/наповнення нового сайту (як у цьому ТЗ) | `quota_coverage` | Гарантує, що жодна категорія не "загубиться" через нерівномірну активність продавців — саме тому обрано за замовчуванням |

> Обидва режими сканують лише 5 наперед заданих категорій (див. розділ 6) — "найновіші" в обох випадках означає "найновіші серед цих 5 категорій", а не по всьому сайту.

### 5.2. `--debug` — діагностичний режим

```bash
python -m teremok_parser --debug
```
Вмикає докладний DEBUG-лог (кожен запит, кожен крок парсингу — видно в консолі) і **зберігає сирий HTML** кожної обробленої сторінки в `output/raw/<run_id>/`. Навіщо це потрібно: якщо парсер щось витягнув неправильно (наприклад, ціну чи дату), можна відкрити збережений HTML і побачити, з чого саме він це витягував — без повторного запиту до сайту. Без цього флагу RAW HTML не зберігається (щоб не засмічувати диск при звичайних прогонах).

### 5.3. `--fail-fast` / `--no-fail-fast` — що робити при "битих" даних

Ці два флаги — протилежності, і **`--fail-fast` увімкнено за замовчуванням**, навіть без явної вказівки в команді:

```bash
python -m teremok_parser                    # так само, як --fail-fast (за замовчуванням)
python -m teremok_parser --no-fail-fast     # явно вимкнути
```

- **`--fail-fast` (за замовчуванням)** — якщо Hard Gate (перевірка інваріантів: дублі по URL, від'ємні ціни, дати з майбутнього тощо) знаходить порушення — експорт файлів **блокується повністю**, пайплайн завершується з помилкою. Жоден файл із потенційно битими даними не потрапить до клієнта.
- **`--no-fail-fast`** — при тих самих порушеннях пайплайн **не зупиняється**, а експортує дані як є, лише залишаючи попередження в лозі. Корисно тільки для розробки/налагодження, коли треба подивитись на "сирий" результат навіть при відомій помилці — **у бойовому запуску цей флаг використовувати не варто**.

Тобто команда `--debug --fail-fast` з прикладу вище фактично означає "докладний лог + збереження HTML для розбору проблем, при цьому захист від видачі битих даних лишається увімкненим" — це найбезпечніший режим для діагностики без ризику випадково отримати неякісний файл на виході.

### 5.4. Встановлення й типовий запуск

```bash
pip install -r requirements.txt
python -m teremok_parser --mode quota_coverage   # звичайний робочий прогін
```

Результат: `output/data/<run_id>/teremok_listings.{csv,json,xlsx}` + `output/reports/<run_id>/teremok_report.json`.

Ключові налаштування — у `config.py`: список категорій, `min_per_category`, `target_total`, ліміти запитів, таймаути.

## 6. Тести й обмеження

```bash
pytest tests/unit -q   # 8/8 passed
```

Тести покривають pipeline, дедуплікацію, вибірку та сховище. **Чесно позначаю прогалину**: немає тестів на самі CSS-селектори витягування полів (`parser/listing.py`) — саме вони найкрихкіші при зміні верстки сайту. Для довгострокової підтримки це перше, що варто додати (тест на "заморожену" HTML-фікстуру сторінки).

Інші відомі обмеження:
- Категорії задаються вручну (5 штук), автовиявлення всіх категорій сайту не реалізовано.
- Версії залежностей у `requirements.txt` не зафіксовані жорстко (`>=`), для продакшену варто запінити.

## 7. Підтримка й розвиток

Архітектура модульна саме для того, щоб додавання нового джерела (нова дошка оголошень, інша країна) або нового поля не вимагало переписування пайплайну — досить нового `parser`-модуля під конкретний сайт. Це відповідає задачі з довгострокової підтримки кількох джерел, описаній у вакансії.
