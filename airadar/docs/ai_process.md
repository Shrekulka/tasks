3. додати нормалізацію та тести крайніх випадків;

**Розподіл ролей.** AI писав чернетки коду, тестів і документації за правилами з `CLAUDE.md`. Я ставив обмеження (P0 → P1 → P2), перевіряв результат командами (`check`, `test`, `collectstatic`, Gunicorn, `curl` по статиці), дивився на сторінки в браузері й у консолі DevTools, читав логи сервера та ухвалював рішення про обсяг. Висновки AI я не приймав на віру: кожну знайдену проблему відтворював або перевіряв за логами (див. розділи про помилки AI).

## Динамічний пошук безкоштовних моделей OpenRouter

P2 не покладається на один заздалегідь зашитий `model`.

`radar/services/llm.py` спочатку отримує список моделей через:

```text
GET https://openrouter.ai/api/v1/models
```

Для цього кроку ключ OpenRouter не потрібен.

Далі модель проходить такі фільтри:

- `pricing.prompt == 0`;
- `pricing.completion == 0`;
- `id` закінчується на `:free`;
- `architecture.input_modalities` містить `text`;
- `architecture.output_modalities` містить `text`;
- `context_length >= 8000`.

Після фільтрації кожна модель представлена скорочено:

```python
{
    "id": "...",
    "name": "...",
    "context": 262144,
    "inputs": ["text", ...],
}
```

Список сортується детерміновано за контекстом (від більшого до меншого), а для однакового контексту за `id`.

**Сортування за розміром контексту не є оцінкою якості моделі.** Це лише спосіб отримати стабільний порядок кандидатів. Для контрольованого пріоритету використовується `OPENROUTER_MODELS`.

Кеш списку моделей:

```python
MODELS_CACHE_KEY = "openrouter:free-models:v1"
MODELS_TTL = 3600
```

Тобто мережевий запит до `/models` зазвичай виконується не частіше одного разу на годину, а `list_free_models` використовує `force=True`, щоб отримати свіжий список.

## Як вибирається конкретна модель

Порядок кандидатів формує `candidate_models()`:

```text
OPENROUTER_MODELS
        ↓
автоматично знайдені free-моделі
        ↓
blocklist / quarantine / duplicate filter
        ↓
MAX_MODELS_TRIED
```

Значення:

```python
MAX_MODELS_TRIED = 5
```

Тому один запит не перебирає весь каталог OpenRouter.

Приклад `.env`:

```env
OPENROUTER_MODELS=model-a:free,model-b:free
OPENROUTER_MODELS_BLOCKLIST=model-b:free
```

Якщо `OPENROUTER_MODELS` порожній, застосунок працює в автоматичному режимі та використовує знайдені безкоштовні моделі.

## Ключі OpenRouter і fallback

Ключі читаються з:

```env
OPENROUTER_API_KEYS=key1,key2
```

або:

```env
OPENROUTER_API_KEYS=["key1","key2"]
```

Загальна стратегія: **модель × ключ**. Для кожної моделі ключі перевіряються послідовно, реакція на помилки типізована:

- успішна непорожня відповідь без символів чужих писемностей (ієрогліфи, хангиль, арабська) повертається одразу;
- відповідь, у якій є символи чужих писемностей, вважається невдалою: перехід до наступної спроби;
- порожня відповідь: перехід до наступної спроби;
- `429`, `5xx`, timeout, `401`: перехід до наступного ключа, потім до наступної моделі;
- `403`: перехід до наступного ключа; якщо `403` отримали **всі** ключі, модель вважається недоступною (а не ключі) і виключається на 10 хвилин;
- `400` або `404`: модель вважається непридатною і виключається на 10 хвилин, інші ключі для неї не витрачаються.

У логах записується номер ключа (`key#1`, `key#2`), але не сам секрет.

## Що робить `llm_enabled()`

```python
llm_enabled()
```

Це дешева локальна перевірка без мережевого виклику. Вона повертає `True`, коли налаштований хоча б один ключ OpenRouter. На сторінці порівняння кнопка вердикту показується, якщо `llm_enabled()` і вибрано щонайменше два сайти.

Наявність ключа **ще не гарантує** успішної відповіді: доступність моделей і мережа перевіряються вже під час `ask_with_fallback()`.

## Захист від ін'єкцій у вердикті

Дані сайтів у промпті обгорнуті в блок `<data>...</data>`, а системний промпт прямо каже, що вміст блоку це дані з чужих сайтів, а не інструкції, і що будь-які команди всередині треба ігнорувати. Це перевіряє `test_verdict.py::test_ok_and_prompt_marks_data_block`. Також є обмеження частоти запитів до вердикту (`test_rate_limit_429`).

## Команда `list_free_models`

Management-команда:

```bash
python manage.py list_free_models
```

реалізована в `radar/management/commands/list_free_models.py`. Вона викликає:

```python
fetch_free_models(force=True)
```

і показує колонки `CONTEXT`, `INPUT`, `ID`.

Це зроблено, щоб не вгадувати назви моделей і не прив'язувати код до старого списку. У поточному середовищі команда знайшла 17 безкоштовних текстових моделей.

Після цього можна вибрати 2–3 моделі й закріпити їх у `.env`:

```env
OPENROUTER_MODELS=id1,id2,id3
```

Автоматичне резервування при цьому лишається: після ручних кандидатів використовуються інші моделі з динамічного списку.

## Живе тестування AI-вердикту (P2)

Перевірено на реальному API OpenRouter: три ключі, безкоштовні моделі.

- Дві перші моделі (`thinkingmachines/inkling-small:free`, `thinkingmachines/inkling:free`) віддали HTTP 403 на всіх трьох ключах. Тобто недоступна модель, а не ключі: той самий ключ на третій моделі спрацював.
- Відповідь дала третя модель (`nvidia/nemotron-3-ultra-550b-a55b:free`). В одному з прогонів перший ключ повернув `bad payload`, і запит успішно завершився на другому ключі.
- Вердикт для трьох сайтів генерувався близько 30 с. За часом у логах майже весь цей час це робота моделі, а відмови 403 разом займають близько секунди.

Каталог не залежить від P2: відсутність ключа, недоступна LLM або проблемна модель не блокують основний функціонал на FreeSerp.

## Де AI помилявся у P2 (OpenRouter)

- Раніше моделі були тільки з env. Замість цього реалізований динамічний `GET /models` і fallback на автоматично знайдені free-моделі.
- Було виправлено вихід із вкладених циклів у fallback: `return` використовується тільки після успішної відповіді, а не `break`, який завершував лише внутрішній цикл. Тест: `test_llm.py::test_429_switches_key_not_model`.
- `429` обробляється на рівні ключа: використовується наступний ключ.
- `400/404` для моделі не призводять до безглуздого повторення з усіма ключами, модель тимчасово виключається. Тест: `test_404_quarantines_model_and_goes_to_next_model`.
- AI запропонував карантин моделі при `403` як рішення «повільного вердикту». Звірка з часовими мітками в логах показала, що це неправда: 403 займають близько секунди, а основний час іде на генерацію. Карантин лишено (він економить зайві запити), але причину затримки в документації вказано правильну. Тести: `test_403_on_all_keys_quarantines_model`, `test_403_on_one_key_does_not_quarantine_model`.
- У відповіді моделі посеред українського слова з'явилися корейські символи, а значення `ai_likely` потрапило у вердикт як «назва білдера». Це знайдено під час живого прогону. Виправлено: промпт уточнено (лише кирилиця, «немає даних» замість `null`, пояснення `ai_likely`), відповіді з символами чужих писемностей відхиляються, у таблиці порівняння `ai_likely` показується як «AI (ймовірно)». У фільтрах і запитах до API лишається вихідне значення. Тест: `test_foreign_script_answer_is_skipped`.
- Не підтверджувався та не вигадувався порядок за «якістю» моделей: сортування за контекстом використовується лише як детермінований порядок.
- У документації та `.env.example` явно вказано, що AI це P2 і необов'язковий.

## Де AI помилявся у каталозі та дашборді (кожен випадок має тест)

- **Графіки «AI» показували весь індекс.** `by_day` і `dr.histogram` зі `stats=1` рахуються по всіх сайтах: у фікстурі `by_day[0] = new.today`, а `ai_startups.today = 0`. Знайдено звіркою сум у фікстурі. Виправлення: підписи «усі ніші», а DR-розподіл по AI тепер рахується окремими запитами `ai_startups=1&dr_min&dr_max` (`get_ai_overview`). Тест: `test_contract.py::test_by_day_is_whole_index_not_ai`.
- **WhiteNoise був описаний у README, але не підключений.** `collectstatic` і Gunicorn працювали, а `/static/` віддавав 404. Знайдено `curl`-перевіркою під Gunicorn. Тест: `test_settings.py::test_whitenoise_serves_static_under_gunicorn`.
- **Адмінка та авторизація при `DATABASES = {}`.** Застосунки admin, auth, sessions не працюють без БД, а `/admin/login/` давав 500. Прибрано разом із моделями й міграціями. Тести: `test_no_apps_that_need_a_database`, `test_admin_url_is_gone`.
- **Один «дивний» домен з API (`a_b.com`, IDN, `null`) давав 500 на весь каталог** через `{% url 'radar:site' %}`. Виправлення: `clean_domain` (IDN → punycode) і відкидання непридатних записів у `search_sites`. Тести: `test_contract.py::test_unroutable_domains_are_dropped_not_crashing`, `test_idn_domain_converted_to_punycode`, `test_views.py::RegressionTests::test_catalog_renders_when_api_returns_unroutable_domains`.
- **Парсер статистики вгадував формат** (`name/count`, `by_day` як dict), а тести перевіряли вигадані форми. Замінено на реальний формат `{"key","count"}` з документації, додано контрактні тести на фікстурах. Тест: `test_normalize.py::ParseStatsTests::test_real_api_shape`.
- **Список ніш обрізався до 8** (обмеження для картки потрапило у фільтр). Тепер фільтр бере всі ніші з API, головна показує `NICHES_ON_HOME`. Тест: `test_contract.py::test_all_niches_available_for_filter`.
- **Поганий пошук:** при `q` завжди йшло сортування за датою. Тепер `sort=auto`: з запитом порядок релевантності віддає сам API. Тести: `test_forms.py::test_auto_sort_uses_api_relevance_when_query_given`, `test_auto_sort_is_newest_without_query`.
- **Налаштування, потрібні коду, не були визначені в `settings.py`** (при ручному перенесенні правок пропущено блок `FREESERP_*`): головна падала з `AttributeError`. Виявлено за трейсбеком на запуску. Тест: `test_settings.py::test_required_settings_defined`.
- **Порівняння не працювало на головній, а вибір губився при переході між сторінками.** Скрипт каталогу завершувався на головній і зберігав вибір лише в пам'яті сторінки. Виявлено вручну: DevTools показав, що на головній немає ні `#cmp-bar`, ні обробників. Виправлено: спільний скрипт для обох сторінок і збереження вибору в `sessionStorage`. Автоматичного тесту немає (у проєкті немає JS-тестів), перевірка ручна: чекбокси на головній, перехід на сторінку сайту, повернення.
- **Таблиця порівняння з шести ручних рядків** замінена на цикл за `COMPARE_FIELDS`. Тест: `test_views.py::RegressionTests::test_compare_table_is_built_from_field_list`.

## Перевірка

Кожен етап проходить:

```text
код → тести → ручна перевірка → документація
```

Для поточного стану проєкту підтверджено:

- `python manage.py test`: 90 тестів, `OK`;
- `python manage.py check`: без системних помилок;
- `collectstatic`: виконується без помилок;
- `python manage.py list_free_models`: список безкоштовних текстових моделей отримується динамічно;
- вручну: головна, каталог, сторінка сайту, порівняння 3 сайтів, AI-вердикт на живому OpenRouter.
